# 프로젝트 분석 및 개선 현황

기준: **2026-09-12 · sAIde 0.1.0**. 최초 코드 분석 후 시스템 보완을 구현했다. 발견한 문제, 적용한 조치, 아직 남은 작업을 구분한다. 실행 계획은 [system-hardening.md](../plan/system-hardening.md), 검사 결과는 [VALIDATION.md](VALIDATION.md)가 기준이다.

## 종합 평가

장시간 모델 호출을 패널에 두고 서비스 워커가 브라우저 작업을 맡는 구조, 모듈별 단위 테스트, 사용자 승인 절차는 유지할 장점이다. 이번 개선은 비동기 작업의 소유권, 실행 직전 대상 검증, 개인정보 삭제와 저장의 경합, 서버 실패 처리에 집중했다.

**현재 28파일/346개 테스트, 타입 검사, 프로덕션 빌드·manifest 검사, 격리된 새 설치 환경의 동일 검사, 실제 Ollama 기본 live 4개가 통과했다.** 실제 확장 설치·권한·다중 창 E2E와 종합 보안 감사를 통과했다는 의미는 아니다.

## R01 — 요청한 탭의 화면만 반환

기존 captureVisibleTab 호출은 요청한 tabId를 사용하지 않았다. 현재 [guards.ts](../src/lib/browser/guards.ts)의 captureTab은 대상 windowId를 지정하고 캡처 전후 활성 탭·URL·로드 상태를 확인한다. 캡처 중 탭이 바뀌었다가 돌아오거나 문서가 다시 로드되는 경우도 이벤트로 감지해 결과를 버린다. 임의로 탭을 활성화하지 않는다.

검증: 다른 활성 탭, 다른 창, 이동 중 캡처, A→B→A 전환, 취소 요청을 모의 Chrome API로 검사했다. **잔여:** 실제 Chrome 다중 창·창 닫기·탭 이동·권한 철회 E2E. 캡처와 상태 검사는 브라우저의 단일 원자적 작업이 아니다.

## R02 — 취소와 타임아웃의 의미

기존 루프는 signal을 전달했지만 실제 실행기가 사용하지 않아 대기가 끝나지 않을 수 있었다. [async.ts](../src/lib/async.ts), [protocol.ts](../src/lib/messaging/protocol.ts), [executor.ts](../src/lib/agent/executor.ts)는 요청 ID·deadline과 취소를 전달하고 signal을 무시하는 Promise도 호출자 관점에서 종료한다. 워커와 주입 스크립트는 실행 전에 유효성을 확인한다. 승인 대상 설명도 15초 제한이며 실패 시 실행하지 않는다.

검증: 무응답 도구, 대상 설명 지연, 스크립트 주입 중 취소, content에 취소가 먼저 도착한 뒤 실행 요청이 도착하는 경우. **제약:** 이미 실행된 클릭·입력·전송을 되돌리는 기능은 아니다. 동기 실행이 끝난 뒤 도착한 취소는 소급 적용되지 않는다. 실제 확장 이벤트 순서는 E2E로 추가 검증한다.

## R03 — 승인한 문서·요소·행동 고정

기존에는 승인 카드 조회와 실행 때 재탐색을 연결하는 식별자가 없었다. [approval.ts](../src/lib/browser/approval.ts)는 content script의 격리된 문서에 토큰을 저장한다. 토큰은 120초 유효·1회 소비이며 URL, 행동 인자, 동일 DOM 노드, outerHTML, 폼 목적지·메서드, 링크 목적지를 비교한다. 변화 시 실행을 거부하고 새 요청이 필요하다. 워커는 extension 문서 sender 및 payload 타입·길이·deadline·URL 스킴을 검사한다.

검증: 동일한 모양의 노드 교체, 폼 목적지 변경, 인자 변경, 토큰 재사용, 잘못된 sender/payload. **잔여:** 같은 노드의 이벤트 핸들러·서버 상태 변경까지 토큰이 보장하지 않는다. 실제 행동의 의미와 결과는 사용자 확인 및 사이트별 E2E가 필요하다.

## R04 — 기억 삭제와 늦은 저장의 경합

기존에는 제외 도메인의 하위 도메인 삭제가 빠졌고 삭제·기억 끄기·큐 종료 뒤 임베딩이 다시 저장될 수 있었다. [memory/store.ts](../src/lib/memory/store.ts)에 공유 정책 세대를 추가하고 삭제와 저장이 같은 DB 트랜잭션 범위를 사용하도록 했다. 큐는 시작 당시 세대와 최신 정책을 저장 직전에 검사한다. 종료 시 네트워크 취소와 저장 차단을 모두 적용한다. 도메인 매칭은 부모와 하위 도메인을 함께 처리한다.

DB v2는 기존 테이블을 보존하고 memoryControl을 추가한다. v1 데이터 보존 migration, 임베딩 지연 중 전체 삭제·제외·비활성화·종료 회귀가 통과했다. 전체 삭제는 미래의 신규 저장까지 끄지는 않으며 기억 끄기는 기존 기록 삭제와 별개다. **잔여:** 실제 여러 패널·설정 문서 간 E2E, 대규모 DB 성능·저장 실패 복구.

## R05 — 대화 작업 소유권

기존에는 탭 조회의 역순 완료, 중복 전송, 중단된 생성의 늦은 결과가 공유 UI 상태를 바꿀 수 있었다. [chat/store.ts](../src/lib/chat/store.ts)는 대화 로드·첨부·생성별 작업 세대를 확인하고 생성 자리표시자에 고유 ID를 부여한다. 전송 전 DB 작업부터 생성 슬롯을 확보한다. [storage/db.ts](../src/lib/storage/db.ts)의 메시지 쓰기는 부모 대화 존재 확인과 저장을 하나의 트랜잭션으로 처리한다.

검증: A/B 역순 조회, 동시 전송, 취소를 무시한 스트림의 늦은 토큰, 탭 변경 뒤 도착한 캡처, 삭제된 대화에 늦게 저장되는 응답. **잔여:** 재생성·삭제·다중 패널을 함께 수행하는 전체 UI 시나리오와 실패 복구 UX.

## R06 — 컨텍스트 예산

기존 buildContext는 pinned 첨부와 최신 질문을 유지하므로 상한을 넘을 수 있었다. 현재 [stream.ts](../src/lib/ollama/stream.ts)는 매 전송마다 메시지·도구 호출·스키마·이미지 비용을 합산하고 numCtx의 70%를 넘으면 HTTP 요청 전에 설명과 함께 거부한다. 에이전트 후속 턴도 같은 경계를 지난다.

**이후 보완:** 컨텍스트를 조립하는 쪽과 전송을 거부하는 쪽이 서로 다른 공식으로 토큰을 세고 있었다. buildContext는 `length / 2.5`와 이미지 262토큰, assertRequestBudget은 estimateTokens(한국어 `length / 2.0`)와 이미지 1,024토큰을 썼다. 그래서 조립기가 예산 안이라고 판단한 요청을 게이트가 되돌려 보냈고, 기본 설정(numCtx 4,096 · 본문 2,000토큰)에서 **본문과 화면 캡처를 함께 붙이면 항상 거부됐다** — 한도 2,867에 게이트 추정 3,191.

두 계산을 [budget.ts](../src/lib/extract/budget.ts)의 `messageTokens`/`promptTokens`/`promptBudget` 하나로 합쳤다. 이미지 비용은 실측값 262로 통일했다. 같은 조건의 현재 추정은 본문만 2,174, 본문+캡처 2,473으로 모두 한도 안이다. pinned 본문은 `fitAttachment`가 전송 전에 예산에 맞춰 줄이고 절단 비율을 고지하므로, 본문 예산을 컨텍스트보다 크게 잡은 설정(본문 8,000 · numCtx 2,048 → 추정 1,179 / 한도 1,433)에서도 거부 대신 축약으로 처리한다. 절단 위치는 대화 길이와 무관해 KV 접두사는 그대로 유지된다. 에이전트는 도구 스키마 비용을 `reservedTokens`로 먼저 빼고 조립한다. 회귀는 두 모듈을 함께 부르는 [context-budget.test.ts](../src/lib/chat/context-budget.test.ts) 11건이 고정한다.

**잔여:** 실제 tokenizer 계산, 도구 호출/결과 쌍을 보존하는 에이전트 이력 축약(루프가 턴마다 쌓는 메시지는 아직 트리밍 대상이 아니다). 이미지 262는 gemma4:e2b 실측이며 타일 예산이 다른 모델의 실제 소비를 보장하지 않는다. 최신 질문 하나가 단독으로 예산을 넘는 경우는 여전히 거부한다 — 사용자의 질문을 임의로 자르지 않기 위해서다.

## R07 — 설정 일관성과 실패 안내

[settings.ts](../src/lib/storage/settings.ts)는 저장 데이터의 타입·enum·수치 범위·모델 이름·HTTP/HTTPS 주소·도메인을 정규화한다. Web Locks로 같은 확장 origin의 read-merge-write를 직렬화하며 잠금 API가 없으면 문서 내 Promise 큐를 사용한다. 기억 정책 변경은 DB 세대를 먼저 갱신한다.

Options는 저장된 설정을 읽은 뒤 최초 연결 확인을 실행하고 ko/en을 반영한다. Options와 MemoryPanel은 저장 변경을 구독한다. endpoint는 편집 완료 시 저장하고 잘못된 URL을 거부한다. 연결 확인은 응답 순서를 검사하고 모델 누락을 성공으로 표시하지 않는다. 기억 설정 저장/삭제 실패를 화면에 알린다.

**잔여:** 실제 여러 설정 탭 조작 E2E, 사용자 프리셋 저장의 동시성 정책, 원격 endpoint의 전용 권한/온보딩. Web Locks 미지원 환경의 대체 큐는 여러 문서 간 잠금이 아니다.

## R08 — 서버 계약과 스트림 오류

[client.ts](../src/lib/ollama/client.ts)는 공통 HTTP 오류 분류와 시간 제한을 사용한다. JSON 요청 기본 15초, embed 180초, 보조 연결 진단 3초다. tags에 기능 정보가 없으면 최대 4개 병렬 show 조회로 보완한다. 에이전트는 tools, 화면을 모델에 보낼 때는 vision을 확인하며 지원 여부가 불명확하면 중단한다.

스트림은 180초간 바이트 수신이 없으면 중단하며 에이전트의 모델 출력 무응답 제한(기본 30초)은 별도로 유지한다. 깨진 JSON, error 청크, done 없는 EOF를 정상 완료로 처리하지 않는다. done을 받으면 연결 종료를 무한히 기다리지 않고 reader를 취소한다.

검증: HTTP 403/404/500, signal을 무시하는 네트워크, 깨진/불완전 스트림, 연결이 열린 done, 예산 초과, 미지원 기능, 실제 Ollama 기본 live. **잔여:** 서버 버전별 fixtures, thinking/embedding 세부 호환성, 전체 정확도 평가. 공식 계약: [모델 목록](https://docs.ollama.com/api/tags), [모델 상세](https://docs.ollama.com/api/show).

## R09 — 데이터 통제와 검색 품질

대화 삭제에 확인을 추가했다. 기억 검색은 보관 기간·제외 도메인·벡터 차원·유한 수치를 확인하고 recall은 최소 유사도 0.2를 사용한다. 잘못된 임베딩은 기존 데이터를 삭제하기 전에 거부한다.

**잔여:** 최근 50건 밖의 대화 검색/페이지 이동, 전체 삭제 UI, 내보내기/가져오기/undo, 첨부 근거 보존 정책, 용량 표시. 벡터는 모델 이름과 차원만 비교하므로 동일 이름의 모델 교체에는 digest와 재임베딩 정책이 필요하다. 0.2는 초기값이며 한국어 검색 평가로 조정해야 한다. 현재 검색은 전체 벡터 순회다.

## R10 — DOM 호환성과 접근성

대상 탐색은 여러 사용 가능한 요소가 매치되면 거부하고 숨김·disabled·inert를 제외한다. 입력은 native value setter와 input/change 이벤트를 사용하며 readonly는 거부한다. 실제 React controlled input fixture에서 앱 상태 갱신을 확인했다.

대화 선택을 버튼으로 바꾸고 승인/대화 창에 Tab 순환·Escape·이전 포커스 복구를 추가했다. 승인은 거부가 기본 포커스이며 포커스 테스트가 통과했다. **잔여:** 다른 요소에 가려진 대상, contenteditable·iframe·Shadow DOM, 사이트별 저장 결과, 320px·200% 확대·스크린리더·고대비 점검. DOM 호출 성공은 서비스의 저장·전송 성공 보장이 아니다.

## R11 — 설치 재현성과 배포 관문

Git이 추적하던 node_modules **4,100파일을 인덱스에서 제거**했다. 로컬 설치 파일은 보존했고 의존성 버전은 변경하지 않았다. Node 24/npm 11 범위, .nvmrc 24.18.0, packageManager npm 11.16.0, Chrome 최소 116을 명시했다.

[CI](../.github/workflows/ci.yml)는 Windows/Linux의 npm ci → compile → test → build → manifest/참조 파일 검사를 구성했다. 격리된 Windows 새 설치 폴더에서도 동일 검사를 통과했다. CI는 아직 원격 실행하지 않았다. 구성 근거: [GitHub Node 검사 안내](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs), [checkout](https://github.com/actions/checkout).

**잔여:** GitHub CI 실제 실행, clean Linux/macOS, 브라우저 E2E, 의존성 감사, ZIP 검증, 라이선스 선택, 공개 개인정보 고지, 스토어 제출. 라이선스는 소유자의 배포·사용 조건 결정이 필요하므로 임의로 정하지 않았다. 설치 검증은 npm 캐시를 사용한 offline ci이며 빈 네트워크 캐시 다운로드 검증은 아니다.

## R12 — 계측·국제화·유지보수

도구 호출만 반환하는 첫 응답도 TTFB에 포함하고 누락된 total_duration이 NaN으로 표시되지 않도록 했다. 대화 상대 시각에 Intl.RelativeTimeFormat을 사용했다. 설정·기억 안내는 원격 서버 사용 시의 데이터 전송을 설명하고 CPU 실험값을 현재 장비의 보장값과 구분한다. README, 아키텍처, 계획·검증·QA 문서와 주요 화면을 현재 코드에 맞췄다.

**잔여:** thinking/content TTFT 분리, 모델 digest·컨텍스트·CPU/GPU별 표본 구분, 오류 문구 전체 번역, 장비 실측·계획서 절 번호에 결합된 주석 정리. 과거 21.5초·131 tok/s·93.8%는 이번 성능 보장으로 사용하지 않는다.
